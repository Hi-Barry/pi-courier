一、结论速览

一句话结论：在 Windows 上「跑起来」大概率没问题，「管起来」（服务化、自动更新）目前是 Linux 专属。

① 桥本体（src/standalone.ts 及其依赖链）几乎全部使用跨平台 Node API：os.homedir() + path.join 构路径、无硬编码 POSIX 绝对路径、无 Unix shell 依赖、附件文件名清洗天然避开 Windows 保留名。E2EE 原生库的安装脚本甚至已经预埋了 win32 分支。

② 卡点集中在外围工具链：npm run build 里的 rm -rf、pi-courier enable/update 硬绑 systemd 与 spawnSync("npm")、找 pi 用的 which 命令——这些在 Windows 上要么直接失败，要么退化为「巧合可用」。

③ 你的使用形态（桥跑在哪都行、Matrix 客户端本来就不挑设备）下，WSL2 路线可以零成本复用现有 Linux 部署经验；如果坚持原生，需要的代码改动很小，但属于「没人验证过的第一批用户」。

三条落地路线对比

按推荐顺序排列。评分含义：10 = 与现有 Linux 部署完全同体验；3 = 能跑但体验残缺。

推荐

路线 A：WSL2

综合评分 9 / 10 · 改造量 0
  • 桥 + pi 全部跑在 WSL2 的 Linux 里，与现有部署100% 同构：systemd user 服务（WSL2 已支持 systemd）、pi-courier enable/update、journalctl 全部照旧可用。
  • 踩坑经验、文档、部署脚本直接复用，无新风险面。
  • 代价：多一层轻量虚拟机；开机自启需要在 Windows 启动项里拉一条 wsl 命令（任务计划程序即可）。
wsl --install -d Ubuntu # 进入 WSL 后与 Linux 完全一致： npm install -g pi-courier && pi-courier setup && pi-courier enable # Windows 侧自启：任务计划程序 → 登录时执行 # wsl -d Ubuntu -u barry --exec systemctl --user start pi-courier
次选

路线 B：Docker Desktop

综合评分 8.5 / 10 · 改造量 0
  • 仓库自带 deploy/docker/（Dockerfile + docker-compose + entrypoint），容器内是 node:24-slim Linux，所有 Windows 兼容性问题整体消失。
  • 适合「Windows 机器只是个宿主」的用法；数据（配置、会话、附件）走挂载卷。
  • 代价：依赖 Docker Desktop（商业使用注意授权）；改配置要进容器或改挂载文件。
# Windows 上装好 Docker Desktop 后： cd deploy/docker docker compose up -d
激进

路线 C：Windows 原生（Node 直跑）

综合评分 5.5 / 10 · 改造量 小（详见第四节）
  • 核心链路（Matrix 收发、pi RPC、附件、提醒、多工程路由）大概率能跑通，本报告第三节逐条给出证据。
  • 但要接受：enable/start/stop/update 等服务管理命令全部不可用；自启要自己用任务计划程序或 NSSM 拉 pi-courier run；可能撞上权限误报警告与 pi 的 Windows 安装毛刺。
  • 适合：喜欢原生、愿意当第一批验证用户的场景。下方命令是「能跑的最低配置」。
# 需要 Node ≥ 22.19（pi 1.0 硬约束，桥有引擎门禁会给人话报错） npm install -g pi-courier # peer 依赖会自动带上 pi pi-courier setup # 配置向导（readline，跨平台 ✓） pi-courier run # 前台运行 # 自启：任务计划程序 / NSSM 包一份 "node ... pi-courier run"
建议：如果 Windows 那台机器只是想「随时随地都能用上 pi」，选 A（WSL2）——它不是妥协，而是把现有整套部署原样搬过去；只有当你明确需要桥进程与 Windows 工程目录直接交互（比如要操作 C:\ 下的项目文件、调用 Windows 工具链）时，原生（C）才有不可替代的价值，届时可以先做第四节那份小改造清单再上。

二、能力矩阵：每个功能在 Windows 上会怎样

「原生可用性」指路线 C（Windows 原生 Node 直跑）下的预期表现。

功能面原生可用性说明与证据
配置向导 pi-courier setup 可用 readline 交互，跨平台。配置写 os.homedir()\.pi\pi-courier.json（src/config.ts:8）。0600 权限位在 NTFS 上被静默忽略——但 Windows 用户目录本身有 ACL 保护，token 不因此暴露给其他本地用户。
前台运行 pi-courier run / Matrix 收发 可用 主链路纯 Node API：矩阵 SDK（matrix-bot-sdk）是纯 JS；无 Unix socket、无 shell 调用。Ctrl+C 优雅退出可用（SIGINT）。
pi 子进程拉起（RPC） 大概率可用，有一处硬伤 上游 RpcClient 用 spawn("node", [cliPath]) 直接跑 js 文件（pi-coding-agent/dist/modes/rpc/rpc-client.js:42），绕开了 .cmd 垫片这个大坑。但桥这边找 pi 用的是 execFileSync("which", ["pi"])（src/rpc/pi-rpc.ts:240）——Windows 没有 which，会抛 ENOENT，然后落到 import.meta.resolve 兜底（peer 依赖通常已随 npm i -g 装在同一棵 node_modules 里）→ 属于「巧合可用」；全局另装的 pi 必须手工设 PI_CLI_PATH 指向 …\@earendil-works\pi-coding-agent\dist\cli.js（指 .cmd 垫片无效）。
E2EE 加密房间 可用 scripts/ensure-crypto-native.mjs:73 已预埋 matrix-sdk-crypto.win32-x64-msvc 命名；sha256 校验/本地缓存逻辑平台无关。你生产实例本来关着 E2EE，更无碍。
附件收发落盘 可用 文件名清洗剥离控制字符/路径分隔符/..，且强制 12 位哈希前缀（src/transports/attachments.ts:37），天然不可能命中 CON/PRN/NUL 等 Windows 保留设备名。目录用 path.join。
多工程 /pmctl（建/迁/删项目房间） 可用 路径解析 ~/ 展开基于 os.homedir()（src/rpc/pmctl-controller.ts:146），默认工程根 ~\Projects 约定成立；文件操作只有 mkdir/unlink，无 shell。
! / !! / /bash（远程跑 shell 命令） 取决于 pi 的 shell 配置 命令由 pi 子进程执行（rpc.bash，src/rpc/message-router.ts:755），不是桥自己跑。pi 自带 bash 工具 + 原生 PowerShell 工具，Windows 上 bash 工具需要 Git Bash 一类的 shell 在 PATH（pi 的 shell 路径可配置）。
systemd 服务族 enable/start/stop/restart/status/logs 不可用 硬编码 systemd user unit + systemctl/journalctl（src/cli.ts:96-126, 173-178）。Windows 替代品：任务计划程序、NSSM、WinSW，包 pi-courier run 即可。
pi-courier update（自更新） 不可用 spawnSync("npm", …) 无 shell:true——Windows 上 npm 是 npm.cmd，Node ≥ 20.12 起 spawn .cmd 不带 shell 直接抛 EINVAL（src/cli.ts:314）；且整个流程首尾都串着 systemctl。Windows 上手动 npm i -g pi-courier@latest 即可替代。
构建 npm run build（仅源码部署需要） 需绕行 rm -rf dist（package.json:20,24）在 cmd 下不存在。绕行：用 npm 发布包（免构建）；或 npm config set script-shell "C:\Program Files\Git\bin\bash.exe"；或手动 rmdir /s /q dist && npx tsc。
优雅关停（服务停止/进程被杀） 降级 监听 SIGTERM/SIGINT（src/standalone.ts:377）；Windows 上 taskkill/服务停止走 TerminateProcess，SIGTERM handler 不会触发 → rpc.stop()、断开 Matrix、清锁文件可能跳过。兜底：PID 锁有陈锁探测（process.kill(pid,0)，Windows 语义可用，src/lock.ts:36-40），重启可自愈。
配置文件权限自检 可能误报 用 stats.mode & 0o777 判断 0600（src/config.ts:20-22）；NTFS 上 mode 值无 POSIX 含义，可能每次启动打一条 "insecure permissions" 警告——吓人但不影响功能。
排障提示文案 文案失配 如 E2EE 故障解法直接写 rm -rf ~/.pi/…（src/standalone.ts:320），Windows 用户照抄会失败（应类比 Remove-Item -Recurse）。纯文案问题。

三、上下游证据（为什么敢说「核心能跑」）

本仓库侧：跨平台卫生做得好的地方

  • 路径全部走 path.join + os.homedir()：配置、PID 锁、Matrix 存储、状态目录、附件目录无一硬编码 POSIX 绝对路径；src/ 下 grep 不到 path.posix，也没有 /usr /var /etc 字面量（仅 i18n 文案与测试里有）。
  • 零 Unix shell 依赖：src/ 运行时代码没有任何 sh -c/bash -c/xdg-open//tmp 直用；仅有的 spawnSync 都在 CLI 的 systemd/npm 管理命令里。
  • E2EE 安装脚本预埋 win32：ensure-crypto-native.mjs 的平台命名函数三分支（win32/darwin/linux×gnu/musl）齐全，下载、校验、缓存全部平台无关。
  • 引擎门禁是人话报错：pi 1.0 要求 Node ≥ 22.19，桥在动态 import 之前用 assertPiEngineSupported 拦截（src/rpc/pi-rpc.ts:307），Node 版本不对时不会让你看一堆 SyntaxError。
  • 状态落盘/提醒/引用缓存全部是普通文件读写（先落盘再跑、原子写），平台无关。

上游侧：pi 本体对 Windows 的态度

事实出处
官方宣称支持 macOS / Linux / Windows 三平台，文档含专门的 Windows Setup 指南pi.dev Quickstart（联网核查，2026-10-10）
带原生 PowerShell 工具（createPowerShellTool / createLocalPowerShellOperations），代码内多处 process.platform === "win32" 分支（config 路径、print-mode 信号注册跳过 SIGHUP 等）pi-coding-agent dist（本机 node_modules 实查）
RpcClient 以 spawn("node", [cliPath]) 拉起子进程——跑的是 .js 文件本体，规避 Windows .cmd 垫片 spawn 限制dist/modes/rpc/rpc-client.js:42
停止子进程用 kill("SIGTERM") + 1 秒后 SIGKILL——Windows 上映射为无条件终止，不影响 RPC 正常性同上 stop() 实现
风险点：社区有「Windows 11 全局装 pi 后找不到 node_modules」的安装 issue（2026-05，Node 26.1 仍复现）——原生装 pi 可能碰毛刺GitHub issue（联网核查）
