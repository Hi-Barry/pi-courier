# 进程韧性专项:JS 异常全局兜底 + 心跳看门狗 + 资源水位守门 + RPC 崩溃自愈(spec,来源 #247)

## Problem Statement

真机实录(Windows Server 2025,C 盘 80GB):同机其他软件写满 C 盘后,桥进程先是 8 分钟内重复刷出 14+ 条 `ENOSPC` 裸 WARN(无任何组件把同一根因聚合为「磁盘已满」的一条告警),随后进程静默死亡——无崩溃日志、无退出记录。部署侧计划任务是登录触发型,进程死了任务状态仍是 Running,不会重新拉起;管理房告警依赖 bot 本身,bot 已死自然发不出。结果是无声离线 9 小时 17 分,次日用户人工上机翻日志才发现并恢复。

定性上这不是磁盘满一个场景,而是一整类「遇障即死 + 死后无痕」的进程韧性缺口:

- **A. JS 层未捕获异常**(磁盘满写失败、异步 bug、插件回调抛错):全库无 `uncaughtException`/`unhandledRejection` 兜底,入口仅有 SIGTERM/SIGINT/SIGBREAK 三个信号处理器,异常逃逸即无声死。本次磁盘满死亡大概率就是 A 类的一个实例。
- **B. Native 崩溃**(matrix-sdk-crypto、onnxruntime、sharp):node 直接死,JS 层救不了,只能靠外部发现。
- **C. 依赖子进程死亡**(pi RPC 子进程崩):主动重启路径存在(`/reload`、登录重启),意外崩溃的自动拉起没有实现。
- **D. 僵死**(活着不干活:事件循环阻塞、同步死锁):外部无法区分「没消息」与「死了」。
- **E. 系统层**(重启后无人登录桌面、进程被杀):计划任务不自启不自愈。

单独修磁盘满是打地鼠;A 类全局兜底一处改动防住整个家族,再看门狗从外部通杀 B/D/E。

## Solution

分五层落地(按性价比排序):

1. **L1 全局兜底(进程内,最优先)**:注册 `uncaughtException` 与 `unhandledRejection` 的统一处理器——结构化记录死因(错误名 + 消息 + 栈,进日志)→ 尽力向管理房发一条「我因 X 崩了」(限时尽力,失败不追)→ 沿与 SIGTERM 同一条优雅退出链释放 pi 子进程、transport 连接与单实例锁后以非零码退出。把「无声死」变成「留言死」,且退出码非零让 POSIX 侧 systemd 的既有 `Restart=on-failure` 能接住拉起。
2. **L2 心跳 + 外部看门狗(通杀 B/D/E)**:桥内周期(默认 30 秒级)原子写一个心跳 JSON 文件(时间戳、PID、版本,顺带写磁盘与堆内存水位);部署侧新增独立看门狗脚本,由系统计划任务/cron 每分钟运行——心跳过期或 PID 不存在即按完整的「杀旧 + 起新」序列重启服务,并用一个不依赖主进程的轻量告警脚本直发 Matrix 管理房(直接读配置里的 token 调 homeserver API)。
3. **L3 资源水位守门(原磁盘满专项降格为此层)**:启动时与周期检查工作盘剩余空间——启动期检查先行于一切网络接线,启动期硬阈值退出只留死因日志不发管理房留言;运行期硬阈值(默认 512MB,可配)沿 L1 同一条「留言退出」链优雅退出;软阈值(默认 2GB,可配)经管理房告警一次(状态翻转去重);桥内写路径上的 `ENOSPC`/`EDQUOT` 失败统一识别、指数退避去重(5 分钟至多一条);顺带堆内存用量监控(超限值比例告警)。
4. **L4 RPC 崩溃自动拉起**:pi RPC 子进程「意外退出」时自动重新拉起(与 `/reload` 等主动重启明确区分),拉起带指数退避与连续失败上限,达上限告警管理房并停止自动尝试(人工 `/reload` 路径照常可用)。
5. **L5 部署文档**:双语 README 写明登录触发型计划任务「不自启不自愈」的权衡,给看门狗的安装步骤(L2 同一产物)与 auto-logon 方案权衡。

## User Stories

1. As a 管理房里的部署者, I want 桥进程因未捕获异常崩溃前收到一条「我因 X 崩了」的死因留言, so that 不用上机翻日志就知道它为什么死、死前发生了什么。
2. As a 管理房里的部署者, I want 磁盘剩余空间跌破软阈值时收到恰好一条告警(而不是每 10 秒一条刷屏), so that 我有时间清理磁盘而告警不变成噪音。
3. As a 管理房里的部署者, I want 磁盘空间恢复正常时收到一条恢复通知, so that 我知道刚才的告警已解除、不需要再处理。
4. As a 管理房里的部署者, I want 磁盘跌破硬阈值时收到死因留言且进程有序退出, so that 状态文件不至于在满盘上写坏,事后日志里能看到死因。
5. As a 管理房里的部署者, I want pi 子进程意外崩溃后自动恢复且会话上下文延续, so that 正在跑的任务断了能自动续上,不需要我手动 `/reload`。
6. As a 管理房里的部署者, I want pi 子进程反复崩溃达上限后收到「已放弃自动拉起」的告警, so that 不会陷入无上限的拉起循环,且知道该人工介入了。
7. As a 部署者, I want 即使桥进程整个死了(native 崩溃/僵死/被杀),仍有独立于它的看门狗发现并重启它, so that 任何一类死亡都不会变成无声离线半天。
8. As a 部署者, I want 进程僵死(还活着但不干活,PID 仍存)时看门狗能先杀掉旧实例再拉起新实例, so that 新实例不会被单实例锁挡死、看门狗不会陷入「每分钟拉起→秒退」的死循环。
9. As a 部署者, I want 看门狗重启服务时用不依赖桥代码的轻量脚本直接给管理房发一条 Matrix 告警, so that 「bot 死了」不再等于「告警通道也没了」。
10. As a 部署者, I want 心跳文件里顺带记录磁盘与内存水位, so that 事后排查时能还原死亡前机器的资源状态。
11. As a 部署者, I want 看门狗告警有冷却窗口, so that 服务反复崩溃时我的 Matrix 收到的是有限几条告警而不是每分钟一条轰炸。
12. As a Windows Server 部署者, I want README 写清楚计划任务登录触发「不自启不自愈」的权衡与看门狗安装步骤, so that 我能照着文档一步到位把自愈补上。
13. As a Linux 部署者, I want README 说明 systemd 已有的崩溃拉起能力、看门狗补上的「僵死检测」差异与重启熔断参数, so that 我能判断自己的部署要不要再看门狗、磁盘持续满盘时不会被无限重启循环刷屏。
14. As a 管理房里的部署者, I want 桥内写盘失败(ENOSPC/EDQUOT)被统一识别并聚合为低频告警, so that 桥自己的写失败不再逐条刷屏消耗所剩无几的磁盘。
15. As a 管理房里的部署者, I want 磁盘跌破硬阈值时进程在重连任何网络之前就退出, so that 磁盘持续满盘时的自动重启循环不会每次都往管理房刷一条死因留言。
16. As a 管理房里的部署者, I want 堆内存用量超限时收到一次告警, so that 内存泄漏能在 OOM 之前被看见。
17. As a 维护者, I want L1–L4 各层都可以独立验收、互不阻塞, so that 可以一票一票落地,坏一层不拖累其他层。
18. As a 维护者, I want 全局兜底与水位守门都以可注入缝接进组合根, so that 单元测试不碰真实 process 事件与真实磁盘。
19. As a 维护者, I want 意外崩溃拉起复用既有的重启生命周期订阅并保留事件监听器, so that 项目预设重放、bash 通道报错终止、agent 事件路由等既有行为在自动拉起后零新增接线即生效。
20. As a 部署者, I want 所有新增用户可见文案中英双语同步, so that 中英文部署看到的告警口径一致。
21. As a 部署者, I want 硬阈值退出与崩溃退出走同一条释放链(pi 子进程、连接、单实例锁), so that 任何退出路径都不会留下锁文件导致重启后单实例守门误判。
22. As a 管理房里的部署者, I want 未配置管理房时这些告警安静降级为只写日志, so that 最小部署不被告警路径打扰。

## Implementation Decisions

- **L1 全局兜底**:新增一个独立的崩溃守卫模块(组合根注入三样缝:日志、管理房通知回调、优雅退出回调),在组合根注册 `uncaughtException` 与 `unhandledRejection`。处理顺序:结构化记录死因(错误名 + 消息 + 栈)→ 尽力发管理房(整条通知限时兜底,如 5 秒,超时放弃;transport 未连接或无管理房则静默跳过)→ 调退出回调。退出回调复用组合根现有的优雅退出链(停 pi RPC → 断 transport → 放单实例锁 → 退出),与 SIGTERM 共用 `shuttingDown` 重入标志防二次进入;**现有退出链把退出码硬编码为 0,必须先参数化**(加一个退出码入参:信号路径照旧传 0,崩溃路径传非零),否则 POSIX 侧 systemd 的 `Restart=on-failure` 对正常退出码不拉起,L1「让既有自愈接住」的核心承诺落空——这是该层落地的第一行改动。处理器内部再抛错时直接 `process.exit` 兜底,不允许兜底自身成为二次崩溃源。`unhandledRejection` 与 `uncaughtException` 同路:Node ≥15 默认本就 crash,显式接管只是把「无序死」换序成「留言 + 有序死」,行为不倒退。现有入口尾部的 `main().catch`(只护启动链)保持不动,运行期逃逸由守卫接住。
- **L2 心跳写侧**:桥内一个周期任务模块,默认 30 秒一 tick,原子写(临时文件 + 改名,与状态文件同契约)一个心跳 JSON 到现有派生状态目录(`~/.pi/pi-courier-state/`,0700 已有):`{ ts, pid, version, diskFreeBytes, heapUsed, heapLimit }`。写失败 fire-and-forget 降级(与状态文件「磁盘是备份」同语义),永不抛。L3 的周期检查与心跳合并在同一个 tick 里,一次定时器干两件事。tick 定时器标 `unref`,不阻碍优雅退出。
- **L2 看门狗(部署产物)**:`deploy/` 下新增看门狗目录:Windows PowerShell 版与 POSIX shell 版各一,外加一个轻量 Matrix 告警脚本。契约:每分钟由系统计划任务/cron/systemd timer 触发;读心跳文件,心跳时间戳过期(僵死)或心跳里的 PID 已不存在(死亡)即判定失能 → **执行完整的「杀旧 + 起新」序列后告警**:
  - **Windows 序列**(两种判定统一走同一序列,平台差异决定次序不能省):① 若心跳里的 PID 仍存活(`Get-Process` 判活)→ `taskkill /F /PID <心跳PID>` 先杀旧实例——单实例锁对活进程持有的锁不抢占(锁文件只在持有进程已死时才可接管),不先杀则新实例报「已有实例在跑」即退,看门狗会陷入「每分钟拉起→秒退」死循环而僵死进程永远除不掉;② `schtasks /end /tn <任务名>` 终止计划任务实例——事故实录里进程死后任务状态仍卡 Running,而任务调度器默认禁止同任务并行实例,不先 end 则随后的 run 被直接拒绝;③ `schtasks /run /tn <任务名>` 拉起。杀完到起新之间无需等锁:旧进程死透后锁文件可被新实例直接接管(既有锁语义),首场景验收必须覆盖「僵死但 PID 存活」分支(造一个占锁假进程写假心跳),不能只测「PID 已死」分支。
  - **POSIX 序列**:`systemctl --user restart` 天然先 stop 后 start,对已死与僵死两种形态都成立,不引入额外步骤。
  - 告警脚本单文件、零桥代码依赖:读 `~/.pi/pi-courier.json` 的 Matrix 凭据与管理房 ID,直接调 homeserver 的房间发送 API,自带网络超时。看门狗自持一个上次告警时间戳文件做冷却(默认 30 分钟),防告警风暴。
  - 心跳文件读不到(首次运行前)不告警——看门狗装好后桥没跑过 first run 属于安装错误,不是进程死亡。
  - 「多久算死」的过期秒数**不进桥的韧性配置段**,只活在看门狗侧:脚本常量默认 180 秒,支持命令行参数覆盖,脚本头注释写明换算关系(默认 180 秒 = 6 × 30 秒心跳间隔)——看门狗按设计零桥代码依赖(只读 Matrix 凭据与心跳文件),若让它解析桥的韧性配置键,用户改了桥配置而脚本仍用默认值,「两端同源」就被打破;改为单一归属(脚本/文档常量),文档与脚本注释互指,桥改心跳间隔时同处调整。
- **L3 水位守门**:新增资源守卫模块,三个职责:
  - 磁盘水位:检查工作目录所在盘的剩余空间(Node 内建 `fs.statfs`,Windows 由 libuv 映射到等价系统调用;部署机 Node v26 已具备)。软阈值(默认 2048MB)与硬阈值(默认 512MB)可配。**检查分启动期与运行期两个时机,次序是本层的关键决策**:启动期检查先行于一切网络接线(在 Matrix 连接与 pi 拉起之前)——磁盘低于硬阈值即退出,只写死因日志、不发管理房留言;这样「磁盘持续满盘 → systemd 拉起 → 启动检查又硬退」的循环每轮都不重连网络、不往管理房刷留言,配合 README 提示的 systemd `StartLimitIntervalSec`/`StartLimitBurst` 熔断参数,循环代价收敛为本地日志一行 + 熔断后停止。运行期(周期 tick)低于硬阈值则沿 L1 的「留言 + 优雅退出」链,死因写明磁盘低于硬阈值。软阈值告警走状态翻转去重(正常→告警发一条、告警→正常发一条恢复),经组合根注入的管理房通知回调下发——与审计日志现有「onDegraded 注入 + 组合根路由 sendReply」同一模式。
  - 写失败聚合:提供统一的故障分类函数(按 `err.code` 识别 `ENOSPC`/`EDQUOT`),挂到既有写路径的失败分支上,聚合计数后按指数退避去重告警(首条立即,之后 5 分钟至多一条)。挂点清单(现状核对口径):状态文件保存、审计日志追加、附件落盘、离线事件台账追加(其现有失败分支只 warn 一行,同属逐条刷屏点)。**聚合边界要写死**:事故里 8 分钟 14 条 ENOSPC WARN 的实际来源是 pi 子进程侧的扩展经子进程 stderr 透传进部署日志,不在桥内写路径里、聚合机制管不到它——「不再刷 14 条」由「软阈值一条告警 + 硬阈值快速退出」达成,验收时不按「maestro 的告警被聚合」字面等。聚合机制覆盖并消除的是桥内四条挂点各自的逐条 warn。不改变各写路径现有降级契约(状态文件保存永不抛、审计故障不放大为可用性故障、台账内存为主磁盘为备份等),只是让「写不进去」这件事可见且不刷屏。
  - 堆水位:每次 tick 比对 `process.memoryUsage().heapUsed` 与堆上限(默认 80% 阈值,可配),超限经同一管理房回调告警一次(同样的翻转去重)。
  - 配置:配置类型新增一个韧性配置段(软/硬阈值 MB、堆告警百分比、心跳间隔秒、拉起上限次数),全部走现有配置派生函数族模式——每条默认值单点解释,缺省/非法值回落默认(与 bash 超时配置同款手编白名单归一),env 覆盖链不新增(配置文件即可,与既有字段一致重启生效)。看门狗过期秒数刻意不在此段(L2 段已述:看门狗侧单点归属)。心跳文件里的版本号字段走既有的桥版本单点读取函数,不新写第二份 package.json 读取。
- **L4 RPC 自动拉起**:改动住在 RPC 包装类内,一条新逻辑:
  - 感知:上游客户端没有公开的子进程退出回调(已核对其类型声明与实现——内部对子进程挂一次性 exit 监听,只做退出错误记录与在途请求拒收)。按既有上游兼容层惯例(该层已有一个直读子进程 stdin 的命名函数),新增一个同界的兼容函数从客户端实例上取子进程引用挂 exit 监听;上游改动时只查兼容层这一处。
  - 区分主动与意外:类内加「预期退出」私有标志,`stop()` 与 `restart()` 置位,**新的客户端实例连上(start 成功)即复位**——生命周期不写死会出另一个洞:若复位只发生在意外拉起路径,一次正常 `stop()` 之后重新 `start()` 的实例,其后续意外死亡会被残留的标志永久误判为预期而失去保护。exit 回调里标志未置位即意外死亡 → 自动拉起。主动路径不计入崩溃计数,行为与现状逐字节一致。
  - 拉起即复用主动重启的完整语义:**按 `restart()` 的既有实现路径拉起,不是裸 `start()`**——现有 `stop()` 会清空事件监听器数组,裸 start 会让 respawn 后的 agent 事件路由全灭;主动重启里「先保存监听器、stop 后恢复再 start」的保留语义必须原样复用,拉起成功后既有 `onRestarted` 生命周期照常触发——项目预设重放、bash 通道「进程已重启」报错终止等既有订阅零新增接线自动生效。
  - 上限与退避:连续意外死亡指数退避重拉(1 秒起步,封顶 1 分钟);连续失败达上限(默认 5 次)停止自动拉起,经组合根注入的回调向管理房发一条「pi 进程反复崩溃已停止自动拉起」告警;此后人工 `/reload`(主动 restart)照常可用且成功后清零计数。
  - 多项目:项目子进程与默认子进程共用同一个 RPC 包装类,自动获得同款自愈,无新增模块。
- **L5 部署文档**:双语 README 各改两处——Windows 章节(现 1.0.0 Windows 支持章节)补「登录触发型计划任务不自启不自愈」权衡说明与看门狗安装步骤(任务计划程序每分钟触发 + 参数说明 + 卸载方法);Linux/systemd 章节说明 `Restart=on-failure` 已覆盖崩溃拉起、看门狗补的是僵死检测与独立告警,并给 auto-logon(自动登录桌面)与看门狗两条路线的权衡。看门狗脚本文件头写安装注释(与现有 systemd unit 文件同风格)。
- **文案**:所有用户可见新增文案(死因留言、磁盘软告警/恢复、硬阈值退出、堆告警、拉起放弃、看门狗脚本消息)进中英双表,中文表为键集基准;看门狗/告警脚本是独立部署产物,其内嵌消息不进 i18n 表,但脚本内消息中英各一版脚本或按部署机语言取其一(实现票定,默认中文注释 + 英文消息,公开仓库口径)。
- **明确不做**(与 issue #247 一致):进程内 supervisor(监督/工作两层架构)、OOM 硬防、Native 模块内部深修、Windows 服务化方案(nssm 等)实现——后者只在文档里写权衡。

## Testing Decisions

- 只测外部行为,不测内部状态字段。新缝全部以注入方式进组合根(与启动状态模块、审计日志 onDegraded 同款),测试不碰真实 `process` 事件监听与真实磁盘。
- 崩溃守卫:注入 fake 通知与 fake 退出回调,断言「异常 → 记录 → 通知 → 退出」的调用顺序、退出回调收到的是非零退出码(信号路径仍为 0——退出码参数化的回归断言)、通知限时后放弃、退出回调二次进入被重入标志挡住、未配管理房时只记日志不抛。
- 水位守卫:注入 fake 磁盘统计与 fake 时钟,断言「跌破软阈值恰好告警一条、回升发恢复一条、反复跨越不发第二条」「启动期硬阈值在任何网络接线(注入的连接 fake)被调用之前就退出,且通知回调零调用」「运行期硬阈值调用退出回调且死因文本正确」「ENOSPC 分类函数识别与退避窗口内最多一条」「堆超限告警一次」。先例:审计日志测试对 degraded 通知恰好一次的断言方式。
- RPC 拉起:沿用 pi-rpc 系列既有白盒注入手法(fake 客户端直塞私有槽),fake 子进程 emit exit 断言:意外死亡 → 自动重拉且**走监听器保留路径(respawn 后 fake 事件仍到达原订阅)**;`stop()`/`restart()` 置位预期标志 → 不触发;「stop → 重新 start 成功 → 再遇意外死亡」仍判意外(标志复位生命周期的回归断言);连续失败达上限 → 告警回调恰好一次且不再重拉;人工 restart 成功 → 计数清零。
- 心跳文件:临时目录集成测试(先例:状态文件测试),断言原子写、内容字段齐全、写失败不抛。
- 看门狗判定逻辑:把「读心跳 + 判过期/判活 + 决定杀杀起起序列」实现为可注入脚本核心(判活命令与任务控制命令作为注入缝),测试断言「僵死(PID 存活)→ 先杀后起」「已死 → 跳过杀直接 end+run」「心跳未过期 → 零动作」三种分支;脚本薄壳只做参数解析与调用核心。
- 双语文案:新增键进双表,由既有 i18n 键集一致测试自动钉住(中文表为锚)。
- 看门狗脚本整壳:仓库门禁做语法级检查(shell `bash -n` / PowerShell 解析),真实拉起与告警行为按 README 步骤在真机验收,不进 vitest。
- 全部落地后跑项目原样门禁:`npm run typecheck && npm test && npm run lint`(管道写法不吃退出码);既有 pi-rpc 系列与审计日志用例必须零改动保持全绿。

## Out of Scope

- 进程内 supervisor(主进程分裂监督 + 工作两层)——外部看门狗已覆盖,复杂度不值。
- OOM 硬防(堆告警可见即可,硬防交给看门狗兜底)。
- Native 模块(matrix-sdk-crypto、onnxruntime、sharp)内部深修——上游问题。
- Windows 服务化替代方案(nssm / Windows 服务包装器)——只写权衡文档不做实现。
- Telegram 等第二 transport 的告警通道——告警只走 Matrix(现状唯一 transport)。
- 看门狗自身的高可用(单实例计划任务足够;看门狗死了等于回到现状,不劣化)。

## Further Notes

- 本 spec 是 issue #247(2026-10-28 拍板的进程韧性专项)的磨细稿,L1–L5 骨架全部保留,粒度落到模块与函数。按项目惯例定稿后发 `[Spec]` issue 并由 to-tickets 在其下拆票;L1–L5 每层可独立成票独立验收。本稿已按 2026-10-28 评审意见修订:Windows 看门狗重启序列(阻断)、退出码参数化、L4 监听器保留与标志生命周期、ENOSPC 聚合边界、启动期硬退次序、看门狗过期秒单点归属。
- 现状核对(2026-10-28,基线 6de6b9a):全库无 `uncaughtException`/`unhandledRejection`/心跳/看门狗;入口仅 SIGTERM/SIGINT/SIGBREAK 三个信号处理器 + 启动链 `main().catch`;优雅退出链退出码硬编码为 0(L1 落地须先参数化);RPC 包装类只有主动 `restart()`(带监听器保留),`stop()` 会清空事件监听器数组;上游客户端无公开退出回调(评审以 npm pack 源码复核 1.0.0:内部 `once("exit")` 只记退出错误 + 拒收在途请求,子进程引用为其公开字段,兼容层路线成立);单实例锁对活进程不抢占、仅持有进程已死才接管(看门狗「先杀后起」序列的依据,也是残留锁不卡新实例的依据);POSIX systemd unit 已带 `Restart=on-failure` + `RestartSec=5`(只管退出不管僵死),Windows 侧计划任务登录触发、无自愈;状态文件/审计日志已有完整的「写失败降级不抛 + 阈值告警一次」先例可循;离线事件台账追加失败仅 warn,是桥内第四个逐条刷屏点。
- 心跳与水位检查共用一个周期定时器是刻意决策:一次 tick 干两件事,定时器数量不翻倍;间隔走桥配置,过期阈值单点归属看门狗脚本常量(命令行可覆盖),文档与脚本注释互指换算关系。
- 首场景回归验证口径(真机,两个分支都要覆盖):①「磁盘满」——人为填满磁盘,期望「一条磁盘告警 → (不清理则)启动期或运行期硬阈值死因退出(启动期无留言)→ 看门狗 end+run 拉起 → 清理后恢复」;②「僵死但 PID 存活」——造一个持锁且心跳停更的假进程(或暂停真进程),期望看门狗先 taskkill 再 end+run、新实例不被单实例锁挡死、告警冷却窗口内至多数条。①分支不再按「maestro 的 14 条 WARN 被聚合」验收(那是子进程 stderr 透传,见 L3 聚合边界),按「软阈值一条告警 + 硬阈值快速退出」验收。
