## Problem Statement

pi-courier 目前的模型是"一个部署 = 一个 bot,一个房间 = 一个 pi 会话",想要多 agent 协作时处处受限:

1. **同一项目想并行多个 agent**:多个会话绑同一工作目录会互踩(共享会话历史、并发改同一工作区)。
2. **跨机器协作没有渠道**:典型场景是 VPS 上开发并部署服务端、本地测试客户端,两台部署的 bot 没法进同一个房间分工干活。
3. **手动拉另一个部署的 bot 进房会出事故**:客座 bot 会把陌生房间的消息当指令执行,落到它自己部署的默认项目上胡乱接活——既危险又答非所问。
4. **bot 之间互不相识**:代码只认识自己的账号,两个 bot 在同一房间可能互相把对方的消息当人类输入,存在互聊回环的风险。

## Solution

不做"一个进程多账号"。**多 bot 的"多"来自多台机器的既有部署**——每台 pi-courier 本来就有一个 bot,单账号的架构假设一根不动:

1. **同项目多房间**:管理房给同一项目开多个房间,可绑已有目录或现开 git worktree(分支级隔离);pi 会话目录每房一份,互不串历史。
2. **协作房间(房主/客座模式)**:房主 bot 对人类消息全响应(现状不变);被拉进来的客座 bot 只响应 @点名,但房间里所有可见文本都通过"增量信箱"进入它的上下文——上下文全量共享,触发权分开。
3. **客座认领流**:客座被拉入陌生房间后不接活,回自己部署的管理房弹确认卡,默认动作 = clone 项目仓库到标准项目根目录,一键确认即以客座模式上岗。项目说明由仓库自带文档承载(README/AGENTS.md),进度同步全交 git,push 分支、人工审核、指定 bot 执行合并。
4. **上下文卫生**:协作房默认不发工具调用流(活卡),用 Matrix 原生"正在输入"表活;房间级 /compact 由各部署各自拦截执行、各压各的会话;客座离线缺口诚实声明,不装知道。

## User Stories

1. As a 开发者, I want 在管理房给同一个项目开多个房间, so that 同一项目能并行跑多个独立会话互不干扰
2. As a 开发者, I want 新建项目房时可选开 git worktree(绑已有目录或现开分支目录), so that 多个会话改同一仓库时不互踩工作区
3. As a 开发者, I want 每个项目房有独立的 pi 会话目录, so that 两个房间绑同一目录时不再抢同一份会话历史
4. As a 开发者, I want 把另一台部署的 bot 拉进项目房间, so that 两台机器能协同开发同一个项目(如 VPS 管服务端、本地管测试)
5. As a 部署管理员, I want 管理房有命令把指定 bot 拉进指定项目房, so that 不用切客户端手动邀请
6. As a 客座 bot 的主人, I want 我的 bot 被拉入陌生房间时不执行任何指令, so that 误邀请或恶意房间不能驱使我的 bot
7. As a 客座 bot 的主人, I want bot 进房后在我的管理房收到认领提示卡, so that 由我决定接不接这个活
8. As a 部署管理员, I want 认领确认卡的默认动作是 clone 仓库到标准项目根目录下, so that 一键确认即可上岗
9. As a 部署管理员, I want 目标目录已存在且 remote 指向同一仓库时直接绑定已有克隆, so that 不重复 clone
10. As a 部署管理员, I want 目标目录名被占用但不是该仓库时被追问, so that 不会覆盖我已有的项目
11. As a 部署管理员, I want 认领时可改绑本地任意已有目录, so that 能复用已 clone 好的代码
12. As a 部署管理员, I want 手工在配置文件里写房间→目录映射仍然有效, so that 老习惯不失效
13. As a 房间主人, I want 我在协作房的消息处理与普通房一致(人类消息全响应;工具流默认关除外), so that 拉客不改变我原来的使用习惯
14. As a 房间主人, I want 客座 bot 只被 @点名才响应, so that 房间不会被多 bot 抢答刷屏
15. As a 客座 bot, I want 房间所有可见文本(用户消息、其他 bot 回复)进我的上下文, so that 被点名时知道前因后果
16. As a 客座 bot, I want 不触发我的消息进增量信箱、被触发时随问题一次性带入并清空, so that 每次点名只带增量,上下文不爆炸
17. As a 客座 bot, I want 我 pi 会话内部的工具调用与中间产物不出现在共享上下文, so that 共享层体积可控
18. As a 用户, I want 协作房里发 /compact 时每个 bot 各自压缩自己的会话, so that 一条命令全员瘦身且摘要互不污染
19. As a 用户, I want 协作房默认不把工具调用流发进房间, so that 共享上下文只剩最终回复文本
20. As a 用户, I want 能按房间手动开关工具调用流, so that 特定房间需要看细节时能打开
21. As a 用户, I want 客座干活期间房间持续显示"正在输入", so that 一眼看出它活着还是宕机/停了
22. As a 用户, I want 客座离线几天回来被点名时被告知缺了多少条消息和时间范围, so that 它不假装知道错过的事
23. As a 开发者, I want 合并由我审核并指定某个 bot 用普通聊天指令执行, so that 合并动作可控且 courier 零改动
24. As a 部署管理员, I want 房间内 bot 身份被登记且 bot 互不触发, so that 不出现 bot 互聊死循环
25. As a 部署管理员, I want 现有单 bot 配置一行不改照常运行, so that 升级零迁移成本
26. As a 部署管理员, I want 单房间绑单目录的现有部署升级后会话与行为完全不变, so that 老部署无感
27. As a 用户, I want 房间携带项目名与仓库地址元数据, so that 任何新进来的 bot 和人一看就知道这房对应哪个仓库
28. As a 客座 bot 的主人, I want 认领确认前 bot 保持静默, so that 目录未定时它不乱答
29. As a 部署管理员, I want 即使两个 bot 互为可信用户也不会把对方消息当 prompt 执行, so that 授权模型在多 bot 房间不失效
30. As a 开发者, I want 协作功能只在明文房承诺, so that 第一版不背包 e2ee 的复杂度
31. As a 部署管理员, I want 确认卡列出完整仓库地址与目标目录, so that 我能在确认前审查要拉取的代码来源
32. As a 客座 bot 的主人, I want 认领卡可以拒绝、且同一房间不重复刷卡, so that 不接活时也不被提示轰炸
33. As a 部署管理员, I want 旧版本 pi-courier 被拉进协作房时保持静默, so that 两端版本不一致时也不出事故

## Implementation Decisions

1. **架构边界**:不做单进程多账号;单账号四层假设(单 matrix 配置对象、单 client、实例级台账、单实例锁)全部不动。多 bot = 多部署各自运行现有单 bot 栈。
2. **角色模型**:房间→项目绑定增加模式字段 `owner | guest`。自建项目房默认 owner;经认领流绑定的房一律 guest;手写配置映射可不带模式(缺省 owner,兼容现状)。
3. **消息路由规则**:owner 房行为与现状一致;guest 房仅 @提及触发;任何模式下,已登记 bot 发送的消息一律只进信箱、不触发、不进入命令解析。@提及判定口径统一为:消息含 Matrix 原生提及标记,或文本显式含 bot 的 Matrix ID / display name(具体实现口径在票内细化,所有 bot 按同一规则判定)。
4. **对端 bot 登记**:认领/绑定时把"本房间内 bot 身份清单"写入房间状态事件(自定义事件类型,内容带写入方署名),读取幂等、重复绑定不重复写。路由器据此识别"谁是 bot"——防回环、防把 bot 当人类授权的根基。
5. **陌生房间安全默认**:未绑定且非管理房/DM 的房间一律不路由、绝不落默认项目;进房(auto-join 行为保持不变)后向本部署管理房发认领提示。**升级影响**:这是对现状的行为变更(现在陌生房会落默认项目接活);对依赖旧行为的部署提供配置开关"允许陌生房落默认项目"(默认关闭,即新安全默认),升级说明须写明此项。
6. **客座认领流**:管理房确认卡,卡面强制展示完整仓库地址与目标目录(元数据来自房间状态事件,展示原样 URL 供人工审查);默认动作 = clone 到项目根(`<仓库名>` 子目录)并 guest 绑定;目录已存在且 remote 吻合→直接绑已有克隆;目录名被占且非同仓库→卡片改问;**拒绝/忽略**→不绑定,同一房间的提示卡不重复刷(本地簿记已提示过的房间);确认前完全静默。手写配置映射仍有效(重启生效,同现状)。认领成功上岗后在房间发一条简短通报,房主可感知客座已就绪。
7. **房间元数据**:项目名 + git 仓库地址(+默认分支)写入房间状态事件;项目房创建时落盘,认领方以此为准 clone;人类可读的房间名同步体现项目名。
8. **增量信箱**:每(部署, 房间)维护一个"未送达可见文本"队列;只收房间可见文本(人类消息、bot 回复终文、活卡终文);**斜杠命令类文本不进信箱**(在解析阶段识别,避免两端重复执行);持有者被触发时以"房间新增消息"前缀并入 prompt 并清空。**信箱有上限**(上限值票内定,超限丢最旧并计数,缺口声明一并说明"另有 N 条早前消息未保留");信箱为内存态,重启丢失由缺口声明兜底。
9. **离线缺口声明**:触发时若存在缺席区间(进程重启/离线积累),prompt 前缀注明"你缺席期间缺 N 条消息(时间范围 X→Y)"。
10. **每房会话目录**:同一 workdir 只有唯一房间时沿用现有固定会话路径(零迁移);出现第二个房间绑同一 workdir 时,新房间改用按房间派生的会话子目录(旧房间保持原路径)。两个 pi 进程同 workdir 的并发文件冲突由 worktree 选项供用户规避,不强拦。
11. **工具流三态开关**:房间级 `showToolCalls: auto | on | off`,默认 auto——owner 单 bot 房=开(现状),含客座的协作房=关。现役全局开关保留为全局默认值,per-room 覆盖优先。
12. **typing 续期**:工具流关闭的房间,pi 回合期间对原生 typing 通知周期续期(现有实现只发一次、10 秒过期),回合结束即停;活卡开启的房间不叠加 typing。
13. **/compact 房间级广播**:房间内的 /compact 由各部署的路由器各自拦截、各自压缩自己的会话,摘要私有互不注入;单 bot 房行为不变。同一"各端各自拦截"模式适用于其他房间级命令(如工具流开关)。命令文本不进增量信箱(见决定 8)。
14. **合并流程**:纯人工——用户审核分支后,以普通聊天指令指定某个 bot 执行合并推送;courier 不新增合并功能。
15. **权限面**:guest 房中面向人类的高权限命令门(访客拦截名单、admin 门、管理房限定)照旧;bot 消息不进命令解析(见 3)。
16. **i18n**:新增文案中英双表同步,以中文表为键集基准(项目质量底线)。

## Testing Decisions

- **只测外部行为**:喂房间事件、断言出站(回复/编辑/typing/状态事件/配置落盘),不断言内部数据结构。
- **主接缝(唯一主缝)**:路由器入站→出站,复用现有 Matrix 假件与 router-* 测试族套路。覆盖:陌生房不接活、guest 只认 @、信箱增量并入 prompt、对端 bot 不触发、/compact 广播、per-room 工具流。
- **会话目录**:项目管理器测试族断言 spawn 参数(每房路径派生、单房场景路径与现状一致)。
- **认领流**:管理房命令 + 配置存储测试套路,断言确认卡文案与绑定落盘、目录冲突分支。
- **元数据/对端登记**:房间操作端口测试族断言状态事件内容与幂等重写。
- **typing 续期**:假时钟(仓库已有先例)断言续期节奏与停止时机。
- **唯一新小缝**:clone 助手的进程级测试(本地 fixture 仓库,不打真网;workdir 测试为风格先例)。
- **门禁**:按 package.json 原样命令跑 typecheck + vitest + biome,管道不吃退出码;宣称全绿前必须实跑。

## Out of Scope

- 单进程多账号 / 多账号配置形态(含账号注册自动化进产品)
- e2ee 加密房的协作(项目房现状恒明文;加密协作列为独立后续里程碑)
- `/compact @bot` 点名压缩
- 客座离线历史自动回填(先做诚实声明)
- bot 自主合并、"领班"自动分派、广播应答模式
- pi 之外的编码工具混搭接入
- 加密房元数据、跨部署管理房互通

## Further Notes

- 决策来源:2026-11-09 的 28 轮需求拷问共识 + 两轮代码勘察 + 一轮规格复查(补入:信箱上限、陌生房默认变更的兼容开关、拒绝认领与防重复提示、确认卡展示完整仓库 URL、@提及判定口径、命令不进信箱、上岗通报、版本互通降级)。勘察确认的三个坑及对策:①进房无门槛且授权只看发信人 → 陌生房不接活 + guest 只认 @;②同目录多房间零防护(共享会话、抢最近会话)→ 每房会话目录 + worktree 选项;③代码不识别对端 bot → 房间状态事件登记。版本互通:旧版部署不识别新状态事件,天然走"陌生房不接活"静默路径,无需专门兼容代码。
- 房间级命令"各端各自拦截执行"是本设计的通用模式(压缩、工具流开关均适用),后续房间级功能优先沿用。
- 施工顺序建议(每票一分支一 PR):① 每房会话目录 → ② 对端 bot 登记 + 陌生房不接活 → ③ 房间元数据 → ④ 客座认领流 → ⑤ 增量信箱 → ⑥ 工具流开关 + typing 续期 → ⑦ /compact 广播 → ⑧ 离线缺口声明 → ⑨ 拉客子命令 + worktree 建房选项。
- 术语表:协作房(含 ≥2 个 bot 的项目房)、房主(owner,自建房且全响应)、客座(guest,认领绑定且仅 @触发)、增量信箱(未送达可见文本队列)、认领(客座侧的确认绑定流程)。
